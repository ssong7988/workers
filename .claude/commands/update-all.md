다음 순서로 진행한다. 각 단계는 이전 단계의 결과를 바탕으로 하므로 순서대로 실행한다.

## 1. 진행 상황 확인

- `git status`로 변경된 파일 전체 목록을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 읽는다. `.gitignore` 대상이나 산출물은 무시한다.
- `git log --oneline -10`으로 최근 커밋 스타일과 흐름을 확인해, 이번 변경이 기존 작업의 연장인지 새로운 작업인지 파악한다.
- 변경 내용을 논리적 단위로 묶을 수 있는지 판단한다 (예: 기능 추가 / 리팩터링 / 버그 수정이 섞여 있으면 분리 커밋을 고려한다). 단, 사용자가 별도로 분리를 요청하지 않았다면 과도하게 쪼개지 않는다.

## 2. 커밋 진행

- 변경과 직접 관련 없는 파일(사용자의 다른 작업 중인 변경, 무관한 포맷팅)은 스테이징하지 않는다.
- 비밀정보(.env, 토큰, 비밀번호 등)가 스테이징 대상에 포함되지 않았는지 확인한다. `report-site/.env`, `REPORT_PATH_TOKEN`, `FINDER_API_TOKEN`, `POSTGRES_PASSWORD`, 루트 `.env`의 `KAKAO_REPORT_URL` 등은 절대 커밋하지 않는다.
- 커밋 메시지는 다음 형식을 따른다:
  - 첫 줄: `<type>: <무엇을 왜 했는지 한 문장>` — `type`은 `feat`, `fix`, `refactor`, `docs`, `test`, `chore` 중 실제 작업 성격에 맞는 것을 고른다.
  - 본문(필요 시): 변경의 배경이나 이유를 1-3줄로 설명한다. 코드가 보여주는 내용(무엇을)이 아니라 왜 바꿨는지에 집중한다.
- AGENTS.md의 커밋 규칙(파괴적 작업 금지, `--no-verify` 금지 등)을 따른다.
- 커밋 메시지 끝에는 다음을 반드시 포함한다:

```
Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
Claude-Session: https://claude.ai/code/session_01QyJfWuG4BG4c8NpzBh7aV3
```

## 3. PROJECT_STATE.md 갱신

- `.agent/PROJECT_STATE.md`를 읽고, 이번 작업으로 실질적으로 바뀐 부분만 갱신한다: 아키텍처, 배포 상태, 진행 중인 작업, 알려진 문제, 주요 결정.
- 이미 사실인 내용을 다시 쓰지 않는다. 날짜나 상태가 바뀐 항목만 손댄다.
- 새 결정이나 트레이드오프가 있었다면 그 배경(왜 이렇게 했는지)도 간단히 남긴다.

## 4. 문서 갱신 (필요한 경우에만)

- 이번 변경이 `.agent/docs/RUNBOOK.md`(실행 방법, 엔트리 포인트)나 `.agent/docs/ARCHITECTURE.md`(구조, 데이터 흐름)에 영향을 주는지 판단한다.
- 영향이 없다면 건드리지 않는다. 억지로 문서를 늘리지 않는다.
- 영향이 있다면 해당 문서에서 실제로 달라진 부분만 정확히 고친다.

## 5. 요약 보고

작업이 끝나면 사용자에게 다음을 짧게 정리해서 보고한다:
- 무엇을 커밋했는지 (커밋 해시와 메시지 첫 줄)
- PROJECT_STATE.md에서 무엇을 갱신했는지 (갱신 안 했다면 그 이유)
- 문서를 갱신했는지, 안 했다면 왜 필요 없었는지
- 실행하지 못한 검증이나 남은 이슈가 있다면 명시

보고는 장문 서술이 아니라 짧은 목록으로 한다.
